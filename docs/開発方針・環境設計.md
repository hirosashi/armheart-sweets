## 2. 実装の土台（推奨案）

**素のPHP 8 + PDO + 自作の軽量な共通部品**を推奨します。

理由:
- さくらのレンタルサーバは Composer / CLI の制約があり、Laravel等は設置・更新の手間とサーバ負荷が大きい。
- 今回の規模（画面11・12.8人日）ではフレームワークの利点より、納品後の保守しやすさが勝る。
- ファイルをSFTPで置くだけで動くため、デプロイが単純。

### ディレクトリ構成（案）

```
/www/system/
├── public/                 ← 公開ディレクトリ（ここをドキュメントルートに）
│   ├── index.php           ← 唯一の入口（front controller）
│   ├── assets/css/app.css
│   ├── assets/js/app.js
│   └── .htaccess           ← URL書き換え・直アクセス防止
├── app/
│   ├── Core/               ← DB接続・ルーティング・認証・入力チェック・ログ
│   ├── Models/             ← テーブル単位のデータ操作
│   ├── Controllers/        ← 画面ごとの処理
│   └── Views/              ← 画面（共通レイアウト + 各画面）
├── config/
│   ├── config.local.php    ← ローカル用（Git管理外）
│   └── config.sakura.php   ← さくら用（Git管理外）
├── db/
│   ├── schema.sql          ← テーブル定義
│   └── seed.sql            ← 初期データ
├── storage/logs/           ← エラーログ・操作ログ
└── install.php             ← 初回のみ使うDB構築用（実行後は削除）
```

- 環境ごとの差分は `config/` のみ。**接続情報はソースに埋め込まない**。
- さくらでドキュメントルートを `public/` に変更できない場合は、`/www/system/` 直下に `public/` の中身を置き、`app/` 等は `.htaccess` で拒否する構成に切り替えます。

### 画面の作り
- 画面はサーバ側でHTMLを組み立てる方式（ページ遷移中心）。
- 一覧の絞り込みや「発注に追加」など、画面を切り替えたくない箇所のみ非同期通信。
- スマホ用の作り込みは今回範囲外。**PC・タブレット（横向き）** を対象。

## 3. ログイン・権限（要決定事項つき）

### 実装方針
- パスワードは `password_hash()`（bcrypt）で保存。**平文保存はしない**。
- ログイン状態はセッションで保持。セッションIDはログイン成功時に再発行。
- 一定時間操作がなければ自動ログアウト（既定 **60分**／要調整）。
- 全画面の先頭で認証チェック。未ログインはログイン画面へ。
- CSRF対策トークンを全フォームに付与。

## 3-2. 日付・時刻の扱い（重要・全画面共通のルール）

日本国内での利用を前提に、**時刻は日本時間（Asia/Tokyo）1本に固定**します。時刻のズレは
「PHP側」「MySQL側」「画面表示」の3か所が別々の基準で動くことで起きるため、
**`App\Core\Clock` という1つのクラスに集約**し、他の場所では時刻を直接扱わない方式にします。

### 決めごと

| 対象 | 固定する内容 | 実装箇所 |
|---|---|---|
| PHP | `date_default_timezone_set('Asia/Tokyo')` を起動時に1回 | `Clock::init()`（`App::boot()` から呼ぶ） |
| MySQL | 接続直後に `SET time_zone = '+09:00'` | `Db::conn()`（`Clock::MYSQL_OFFSET` を使用） |
| DB保存値 | `Y-m-d H:i:s`（日本時間の文字列）／型は `DATETIME` | `Clock::now()` |
| 画面表示 | `Y/m/d H:i`（日付のみは `Y/m/d`） | `Clock::dt()` / `Clock::d()` / `View::dt()` / `View::d()` |
| 週の基準 | 月曜日はじまり | `Clock::weekStart()` |

### コードの書き方（禁止と推奨）

- 使わない：`date()` `time()` `new DateTime()` `strtotime()` `NOW()` を各画面・各処理に直接書く
- 使う：`Clock::now()` `Clock::today()` `Clock::minutesAgo()` `Clock::daysLater()`
  `Clock::daysUntil()` `Clock::weekStart()` `Clock::dt()` `Clock::d()`

`TIMESTAMP` 型は使わず `DATETIME` 型で統一します（`TIMESTAMP` はサーバのタイムゾーン設定で
値が読み替えられ、ズレの原因になるため）。

### 確認方法

- `php tests/clock_test.php` … 書式・週の計算・期限計算と、**PHPとMySQLの時刻が一致するか**を検査
- ホーム画面の「時刻の確認（日本時間）」… システムの時計とデータベースの時計を並べて表示。
  現場の方でもズレに気づけるようにしています（画面下にも常時、日本時間を表示）

将来サーバを移す場合も、上記2か所（`Clock::init()` と `Db::conn()`）だけで日本時間へそろいます。

## 4. データベース設計（MVP範囲）

文字コード `utf8mb4` / 照合順序 `utf8mb4_ja_0900_as_cs_ks` は使わず `utf8mb4_general_ci`（さくらでの互換性重視）/ タイムゾーン `Asia/Tokyo`。
全テーブルに `created_at` `updated_at` `created_by` `updated_by` を持たせ、削除は原則 `deleted_at` による論理削除。

| # | テーブル | 内容 | 今回範囲 |
|---|---|---|---|
| 1 | `users` | 利用者（ログインID・パスワード・役割） | ○ |
| 2 | `login_attempts` | ログイン失敗の記録（ロック判定） | ○ |
| 3 | `operation_logs` | 操作ログ | ○ |
| 4 | `suppliers` | 業者 | ○（画面は簡易のみ） |
| 5 | `materials` | 原材料（単位・単価・仕入単位・賞味期限管理有無・業者） | ○（画面は簡易のみ） |
| 6 | `products` | 商品（スイーツ） | ○ |
| 7 | `parts` | パーツ（スポンジ・クリーム等の半製品） | ○ |
| 8 | `product_parts` | 商品→パーツ構成（1商品あたりの個数） | ○ |
| 9 | `product_materials` | 商品→原材料の直接配合 | ○ |
| 10 | `part_materials` | パーツ→原材料の配合 | ○ |
| 11 | `production_plans` | 週次生産計画（週・商品・数量） | △ 入力手段が要決定 |
| 12 | `part_progress` | パーツ別生産進捗（未着手／製造中／完成） | ○ |
| 13 | `inventory` | 原材料在庫（数量・ロット・賞味期限） | ○ |
| 14 | `inventory_adjustments` | 棚卸し調整の履歴 | ○ |
| 15 | `purchase_orders` | 発注（発注番号・業者・状態・日付） | ○ |
| 16 | `purchase_order_items` | 発注明細（材料・数量・単価・金額） | ○ |

### 必要量計算の考え方
```
商品の生産数 × product_parts.数量 × part_materials.配合量  ＋  商品の生産数 × product_materials.配合量
　→ 材料ごとに合計 ＝ 必要量
　　必要量 − inventory.在庫数 ＝ 過不足
　　　過不足 > 0                → 「足りない」（赤）
　　　0 ≧ 過不足 かつ 在庫 < 必要量×1.2 → 「あぶない」（黄）
　　　それ以外                  → 「足りている」（緑）
```
> 「あぶない」の判定（上記の 1.2 倍＝2割の余裕）は要決定事項です。日数基準（例: 3日分を切ったら）にも変更可能。
